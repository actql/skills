# Build an ActQL Connector

A Connector connects ActQL to one external system. A Program sees only
names such as `conn.resource`; authentication, paging, rate limits and the
shape of the API stay inside the Connector. This skill is for a system that
is not among the 17 Connectors ActQL ships with. Start with
`references/connectors/authoring.md`; it defines every piece below.

## 1. Decide the contract before any code

Work through the eight sections every Connector page has, and write the
page first (`references/connectors/README.md` lists the sections; use
`references/connectors/salesforce.md` for a SaaS API and
`references/connectors/gcs.md` for an object store as models):

1. **Sources**: each resource, its columns, its **key**, and how far a read
   may reach (paging, filters the system can apply). A file-capable system
   also exposes a listing source (`LIST_FILES(conn.listing, …)`) and a
   `contents` source joined on `resource` and `version`.
2. **Types**: the system's types and the ActQL types they become; where
   precision is kept and where a type is unsupported. Nothing is coerced
   silently; a value that does not fit fails `check` when known statically
   and the item otherwise.
3. **Effects and operations**: record Effects (`INSERT`, `UPDATE`,
   `UPSERT`, `DELETE` by the declared key), `STORE` for content or rows,
   `CREATE TABLE` where there is a catalog, and every operation as an
   `EFFECT COMMAND conn.op [TARGET …] ID … [INPUT …]` contract. Full
   support means everything the system can do through its API is
   reachable; do not leave half the write surface undeclared.
4. **Setup**: the connection entry, the credentials (`{"env"}` /
   `{"path"}`), the permissions the account needs, and what ActQL Cloud
   offers.
5. **Capabilities and pushdown**: which operations run inside the system and
   the exact conditions under which they keep ActQL's meaning (NULL,
   collation, numeric precision). A Capability is never a permission.
6. **Preview and reconciliation**: Preview strength is `full_diff` (current
   values read first, write conditioned on a version, etag or hash) or
   `targeted` (exact targets and new values, verifiable at apply time).
   There is no weaker strength: an Effect whose targets cannot be resolved
   before sending cannot be declared. A changed target ends the item
   `failed` with `conflict`. A lost reply is reconciled only through
   evidence the Connector itself recognises: a request marker the system
   stores, an idempotency key, a job id, a timeline event. Matching values
   or timestamps are not evidence, and nothing is ever resent.
7. **Limits and cost**: paging, rate limits, read ceilings, what the system
   charges.
8. **Example**: one read-only Program and one with an Effect or operation.

If a section cannot be filled honestly (for example, the API offers no
marker for deletes), say so on the page: those items stay `unknown` on a
lost reply. That is correct behaviour, not a gap to paper over.

## 2. Implement the declarations

`references/contributing/connector-authoring.md` is the in-repository
mechanics: where the code lives, the installation manifest and compute
bundle it declares, what the common Host owns (Effect ledger, claim, send,
response capture, unknown handling, recovery) and what the driver supplies
(request building, response classification, type conversion). Do not add a
second retry or cleanup owner, a provider-name branch in the common Host,
or a reinterpretation of the Run state machine: the MoonBit Core decides
when work is complete; the driver executes.

Markers and idempotency keys are generated by the common owner and bound to
the Effect item before sending; the driver's job is to place them where the
system will store them and to find them again.

## 3. Prove it

The tests a Connector must pass are listed at the end of
`references/contributing/connector-authoring.md`. In short, with an
independent fixture: types and NULL/missing round-trip; target binding;
failure classification; write counts on the public Local and HTTPS paths
(0 before approval, 1 after, none after a restart); `unknown` on a lost
reply; cleanup retry. Never compute expected fixtures from the product's own
output.

Then record what runs: the Connector gets a row on
`references/reference/status.md` (read / record Effects / tables and
content / operations / Preview and reconciliation), each cell implemented,
experimental or planned, and the page describes the full v0.1 surface
regardless.

## 4. Where it goes

During v0.1 the ActQL repository takes Connector changes from the
maintainers only (`references/contributing/README.md`). The place for
Connectors built outside the repository, and how they are distributed and
installed, is being decided; until then, keep the Connector in its own
repository following the same layout and tests, so it can be adopted
without rework. Do not open a pull request to the Core for it.

## Gotchas

- The key named by `ID` must identify exactly one record. If the system
  does not enforce uniqueness, verify it when building the Preview and
  fail items that match several records.
- Logical items and physical requests are different things: a hundred
  `UPSERT` items may travel as one batch request, but each keeps its own
  identity, Preview entry and outcome.
- Sends, posts, refreshes and jobs are Commands, with `ID` for the item and
  `TARGET` only when the contract needs a per-row resource.
- Secrets live in the Host, never in the manifest, the page or a fixture.
